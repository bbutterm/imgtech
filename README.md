# imgtech — сравнение версий PDF-чертежей

Сервис принимает две версии PDF-комплекта (CAD-чертежи и текстовые листы),
находит отличия на уровне векторной геометрии и текста, показывает их
рамками на разворотах «бок о бок» и позволяет согласовать каждый лист
с выгрузкой DOCX-отчёта.

**Прод:** https://imgtech.vercel.app (ветка `main`)
**Тестовый стенд:** preview-деплой ветки `dev` (Vercel собирает автоматически)

---

## Архитектура

```
браузер (React SPA)
  │  вход по email/паролю ─────────────► Supabase Auth
  │  файлы >3.5МБ ─────────────────────► Supabase Storage (bucket uploads)
  │  одна активная сессия ─────────────► Supabase Postgres + Realtime (table sessions)
  │
  │  /api/plan, /api/compare-batch (Bearer-токен)
  ▼
Vercel serverless (Python, FastAPI)  ── проверка токена ──► Supabase /auth/v1/user
  │
  ▼
ядро сравнения (numpy + PyMuPDF), файл core/vector_compare.py
```

Серверного состояния нет: файлы живут в Storage только на время сравнения
(клиент удаляет их в `finally`), результаты и отметки согласования —
в памяти вкладки.

## Как работает ядро (core/vector_compare.py)

1. **Извлечение**: `page.get_cdrawings()` (сырые кортежи из C — в разы быстрее
   `get_drawings`), отрезки/кривые Безье/прямоугольники сэмплируются в облако
   точек с шагом `step=2.0` pt пакетно через numpy. Представление инвариантно
   к порядку путей, разбиению линий и способу аппроксимации дуг — «шум
   экспорта» из CAD не даёт ложных срабатываний.
2. **Регистрация сдвига**: перебор целочисленных сдвигов ±8 pt по сетке
   заполненности (максимум совпавших точек), затем локальный перебор с шагом
   0.25 pt. Медиана смещений до ближайшего соседа НЕ используется намеренно —
   на осевых линиях она систематически уползает (см. комментарий в коде).
3. **Сопоставление**: точка совпала, если в другом облаке есть точка ближе
   `eps=1.5` pt. Поиск — клетки размером eps, упаковка индексов клетки в
   int64-ключ, кандидаты через `searchsorted`, точная евклидова проверка.
   В обе стороны.
4. **Кластеризация сирот**: связные компоненты клеток 10 pt, минимум 6 точек,
   bounding box + отступ 3 pt.
5. `unmatched_share` > 0.6 в возврате — представления несовместимы
   (например, скан): вызывающий код должен считать это «нельзя сравнить
   векторно», а не «всё изменилось».

Производительность: лист A1 со ~100k путей — ~3 c (350–400k точек).
Профилировалось: главный остаток времени — C-код `get_cdrawings` PyMuPDF.

## API (api/index.py)

Все эндпоинты требуют `Authorization: Bearer <supabase access_token>`.
Проверка — сетевой вызов `GET {SUPABASE_URL}/auth/v1/user` (без секретов
на сервере). Ошибки: 401 (нет/плохой токен), 400 (плохие данные), 502
(хранилище недоступно).

| Эндпоинт | Вход | Выход |
|---|---|---|
| `POST /api/plan` | multipart `file1`,`file2` | план (см. ниже) |
| `POST /api/plan-urls` | JSON `{url1,url2}` — подписанные ссылки Storage | план |
| `POST /api/compare-batch` | multipart + поле `pairs` (JSON-строка, ≤12 пар) | `{pages:[…], elapsed}` |
| `POST /api/compare-batch-urls` | JSON `{url1,url2,pairs}` | то же |
| `POST /api/compare`, `/api/compare-urls` | как выше, без pairs | страницы 1:1 — legacy/ручная проверка, фронт не использует |

**План** — сопоставление страниц по содержимому (difflib по спискам слов,
окно ±10 от диагонали, жадное связывание, порог 0.5):

```json
{ "pairs": [[0,0],[1,1],[11,17]], "removed": [15,44], "added": [13],
  "numPages1": 50, "numPages2": 49 }
```
`removed`/`added` — 0-based индексы листов без пары (удалён из док.1 /
добавлен в док.2).

**Страница** в ответе партии:

```json
{ "index1": 11, "index2": 17,
  "boxes1": [[x0,y0,x1,y1],…], "boxes2": […],
  "textBoxes1": […], "textBoxes2": […],
  "width1": 1191, "height1": 842, "width2": …, "height2": …,
  "unmatchedShare": 0.03, "heavilyChanged": false, "truncated": false }
```

Постобработка на пару страниц:
- текстовые рамки, накрытые графическими (перекрытие ≥50%), поглощаются;
- соседние рамки склеиваются: графика — зазор ≤15 pt, текст — ≤12 pt
  (несколько слов подряд = одно отличие);
- `heavilyChanged` (share > 0.5): вместо мелочи — до 30 зон изменений,
  склейка с зазором 40 pt;
- потолок 100 рамок на пару: остаются крупнейшие, `truncated: true`.

URL-ы для скачивания жёстко проверяются на префикс
`{SUPABASE_URL}/storage/v1/object/sign/uploads/` (анти-SSRF), лимит
скачивания 60 МБ/файл.

## Фронтенд (frontend/src/App.jsx)

Поток сравнения (`Workspace.handleCompare`):
1. Сумма файлов < 3.5 МБ → multipart напрямую (лимит тела запроса Vercel
   ~4.5 МБ); иначе → загрузка в Storage `uploads/{uid}/{jobId}/…`,
   подписанные ссылки на 1 час, после ответа файлы удаляются.
2. `plan` → прогресс-бар с реальным счётчиком → партии по `BATCH_SIZE=6`
   пар, результаты дорисовываются по мере прихода.
3. Просмотр: пары рендерятся **лениво** (IntersectionObserver, зона 500 px),
   разрешение канваса 2800 px (или 1600, если пар > 8) — иначе вкладка
   падает по памяти на больших комплектах. Зум колесом (до 24×) и
   панорамирование синхронны для двух документов (общий transform-state
   на пару).
4. Навигация «Отличие N из M → показать» скроллит и зумирует обе страницы
   к рамке; активная рамка пульсирует.
5. **Согласование — по листам, не по отличиям** (требование заказчика):
   галочка + комментарий в заголовке каждой пары/удалённого/добавленного
   листа; согласованный лист — зелёная полоса и зелёные рамки; выгрузка
   DOCX (`report.js`): таблица «№ / Лист / Изменения / Статус / Комментарий».
   Отметки живут только в памяти вкладки (персистентность — в бэклоге).

Auth/сессии: `supabase.auth.signInWithPassword`, регистрация в приложении
отсутствует (аккаунты создаёт админ). Единственная активная сессия:
при входе пишется `sessions.sid` (uuid), остальные устройства ловят
изменение через realtime `postgres_changes` и разлогиниваются.
`localStorage['imgtech-sid:{uid}']` хранит sid этого браузера; свой вход
не выбивает сам себя, потому что sid пишется до подписки.

## Инфраструктура

- **Vercel**: прод = `main`, каждая ветка = preview с URL
  `imgtech-git-<ветка>-bbutterms-projects.vercel.app`. Функция:
  `maxDuration 60`, регион `pdx1` (рядом с бакетом us-west-2).
  Лимит тела запроса ~4.5 МБ на всех тарифах — потому и Storage-путь.
- **Supabase** (проект `ajltzwomvyvntvtjnrrf`, us-west-2): Auth
  (email/пароль), Postgres (`sessions` + RLS «только своя строка»,
  realtime-публикация), Storage (bucket `uploads`, приватный, RLS
  «папка = свой uid», лимит 50 МБ/файл).
- Схема накатана миграцией `sessions_and_uploads` (см. Supabase migrations).
- **Ветки**: `main` — прод; `dev` — разработка; `release/v0.1-demo` —
  замороженная точка отката (ветка-закладка: пуш git-тегов из CI-сессии
  был заблокирован).

## Локальная разработка

```bash
pip install -r requirements.txt uvicorn httpx
uvicorn api.index:app --port 8000          # API
cd frontend && npm install && npm run dev  # UI на :5173, /api → :8000

python3 -m core.tests.run_tests            # тесты ядра (13 проверок)
```

Тестирование API без доступа к Supabase (проверка токена — сетевая):
монкипатч `api.index.verify_token = lambda t: {"id": "test"}` +
`fastapi.testclient.TestClient`. Полный UI-прогон в браузере: Playwright
с перехватом `**/auth/v1/token**` и `**/rest/v1/sessions**` (fulfill
фейковой сессией) — рецепт в истории коммитов работал для проверки
экрана результатов без реального входа.

## Правила сопровождения (ОБЯЗАТЕЛЬНО для следующего исполнителя)

1. **`api/vector_compare.py` — копия `core/vector_compare.py`.** Правишь
   ядро → синхронизируй копию (заголовок-примечание сохранить). Причина:
   serverless-функция Vercel должна быть самодостаточной.
2. **В `main` не пушить без явного «выкатывай» от владельца.** Работа идёт
   в `dev`, владелец проверяет preview, потом merge.
3. После правок ядра — прогнать `python3 -m core.tests.run_tests` и
   эталонные реальные пары (у владельца: комплект «Тульская ул.», где
   известны все отличия: удалённый узел, значок BGB1.18, удалённые листы).
4. Пороги подобраны на реальных чертежах владельца — меняя, перепроверяй
   на них: `eps=1.5`, `step=2.0`, `HEAVY_SHARE=0.5`, `MAX_BOXES_PER_PAGE=100`,
   склейка 15/12/40 pt, `MATCH_MIN_SIM=0.5`, `MATCH_BAND=10`,
   фронт: `DIRECT_LIMIT_MB=3.5`, `MAX_FILE_MB=50`, `BATCH_SIZE=6`.
5. Ключи в `frontend/src/supabase.js` и `api/supabase_auth.py` — публичные
   (anon/publishable), это нормально. Секретов в репозитории нет и не должно
   появиться.
6. Демо-аккаунты создаются администратором (SQL-вставка в `auth.users` +
   `auth.identities`, пример в истории). Самостоятельную регистрацию в
   Supabase (Auth → Sign In/Providers → Allow new users to sign up)
   держать ВЫКЛЮЧЕННОЙ.

## Известные ограничения и бэклог

- Регистрация листов — только параллельный перенос: поворот/масштаб листа
  даст ложные отличия по всему полю.
- Перемещённый элемент = два отличия («удалено здесь» + «добавлено там»),
  связывание «было→стало» не реализовано.
- Сканы (растровые PDF) не сравниваются — помечаются `heavilyChanged`;
  растровый fallback (SSIM) в бэклоге.
- Атрибуты линий (цвет/толщина) не сравниваются.
- Отметки согласования не сохраняются между сессиями (нужна таблица в
  Supabase Postgres — «история сравнений»).
- При глубоком зуме канвас мылится (фикс — динамический ре-рендер видимой
  области под текущий масштаб).
- `VIEW_W` вычисляется один раз при загрузке — поворот телефона не
  пересчитывает раскладку.
- Страницы без слов сопоставляются по диагонали (пустые списки слов дают
  похожесть 1.0) — для чисто графических комплектов нужна векторная
  подпись страницы в `build_plan`.
- Legacy-каталоги `img/`, `cleaner/`, `nginx/` подлежат удалению после
  полного перехода (внимание: `img/config.py` содержит реальные email-адреса).
